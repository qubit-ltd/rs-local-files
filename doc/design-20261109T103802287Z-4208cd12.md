# RLF6-001 条件写入 fuzz 有效性修复设计

## 范围与授权

纳入本轮全部评审意见：**RLF6-001（P2）：条件写入 fuzz 入口静默退化，且缺少 Rooted 随机探索**。用户未限定采纳子集；没有明确搁置或拒绝的条目，没有待验证疑点需要先升级为缺陷。

本次方案生成阶段仅写本设计及配套实施计划；两份文档交付即结束本阶段，不进入实施。下一阶段按实施命令授权开展代码、测试及验证工作，不继承本阶段的只读实施边界。继续使用当前 Paseo workspace，不创建或打开新的 Paseo workspace。

## 已确认事实

当前检查基线 HEAD 为 `a496b818`，实施时应重新记录完整 SHA 和工作树差异。工作树已有 `Cargo.lock`、`fuzz/Cargo.lock` 改动以及两份旧方案文档删除，均不是本方案生成操作产生，不得覆盖或恢复这些用户改动。

- `fuzz/fuzz_targets/conditional_lifecycle.rs:20–27`：启用 `conditional` 才调用条件模型，未启用时调用普通 lifecycle；条件分支固定传入 `false`，只探索 Host。
- `fuzz/Cargo.toml:17–18,29–34`：`conditional` 非默认，目标没有 `required-features`。
- `fuzz/fuzz_targets/conditional_model_tests.rs:15–20`：已有固定序列同时验证 Host、Rooted 和 witness oracle，不能替代随机探索。
- `.github/workflows/ci.yml:164–183`：Linux 项目额外验证编译两种 fuzz 配置并运行固定模型测试，不能单凭这些步骤声称执行了条件模型随机探索。
- `.infra/ci/ci.toml` 配置默认 smoke。邻接本地基础设施 `rust-infra/rs-infra-verify/src/fuzz.rs` 的通用调用没有传目标 feature。本轮没有核对远端共享 workflow 的实际运行，不能推断所有远端 CI 均未运行 fuzz；`fuzz-check: false` 也不足以证明 CI 完全没有 fuzz。

以上是测试有效性缺口，不是已证实的数据损坏或生产安全缺陷。

## 方案选择

选择最小的项目内修复，不修改共享 rs-infra 工具、不升级依赖、不新增 fuzz target。

1. fuzz 子包增加 `default = ["conditional"]`，目标增加 `required-features = ["conditional"]`。删除普通 lifecycle 回退。这样通用默认构建/运行仍能工作，而显式关闭默认 feature 的调用必须显式启用 conditional，不能假成功。
2. 同一 libFuzzer 输入依次调用 `conditional_model::run_model(data, false)` 和 `conditional_model::run_model(data, true)`，保留现有 bounded 模型、临时资源清理及 witness oracle。两个 namespace 使用独立 fixture；不把前一轮状态传给后一轮。
3. Linux `verify-extra-script` 保留现有编译和固定模型回归，再显式运行带 `--features conditional` 的条件 target smoke，时限 10 秒、最大输入 4096 字节。失败保留复现输入并记录其路径；日志必须显示实际进入 libFuzzer、执行了输入、正常结束，不能用仅编译或零测试成功代替。

未选方案：新增独立 Rooted target 会增加配置和 smoke 数量；输入首字节选择 namespace 会改变既有输入解释并使短期 smoke 两种模式的覆盖依赖随机选择。对当前有界模型，同一输入运行两次更直接。仅加 required-features 则可能使无 feature 的通用执行器失败或跳过目标，不能单独解决默认路径问题。

## 文件职责及兼容性

| 文件 | 预期变化 |
| --- | --- |
| `fuzz/Cargo.toml` | fuzz 子包默认 feature 与 target feature gate |
| `fuzz/fuzz_targets/conditional_lifecycle.rs` | 唯一条件模型入口；每个输入运行 Host 和 Rooted |
| `.github/workflows/ci.yml` | Linux 显式条件 fuzz smoke 和失败证据记录 |
| `fuzz/fuzz_targets/conditional_model_tests.rs` | 保留已有固定回归；仅在确有覆盖缺口或失败时补充行为用例 |

不改变生产库 `Cargo.toml` 的默认 feature、公共 API、文件系统语义和数据格式。`rs-fs-local`、`rs-mime`、`rs-magika` 等调用方无需迁移。开发者若使用 `--no-default-features` 运行该 fuzz target，需加 `--features conditional`；普通 lifecycle 仍使用自身原有 target。

默认启用 conditional 只改变不发布的 fuzz 子包，可能增加其他 fuzz targets 构建时的依赖/测试支持编译成本；这是兼容现有通用执行器的局部代价，不扩展到生产构建。同一输入运行两种模式会降低单位时间输入吞吐量，但保证每个输入都探索两套后端，继续采用现有 10 秒预算，不承诺长时间 fuzz 的缺陷发现能力。

## 验证及验收

- 默认 target 构建成功，实际运行条件模型；显式禁用默认 feature 且未启用 conditional 时明确拒绝构建；显式启用后恢复成功。
- 固定回归继续执行全部十组序列的 Host/Rooted witness 断言；fixture 创建失败仍由固定测试显式失败，不把 `run_model` 返回 `None` 当作模型成功证据。
- 在支持 Rooted 条件写入的平台上，实际 libFuzzer smoke 无 panic/崩溃；日志有实际输入执行记录。两次模型调用的覆盖证据由源码审查与 Host/Rooted 固定回归共同建立，不能只凭 fuzz 进程退出码认定两种模式均执行。
- Linux CI 显式命令运行；已有 Windows/macOS 条件回归不削减。保持既有全量验证、覆盖率和静态检查阈值，不跳过失败目标。
- 下一阶段允许为测试失败、`ci-check.sh` 错误或覆盖率不足新增/修改测试及必要生产源码，包括已有基线问题；须记录原因并保持改动与验收恢复相关，不以统一风格或潜在扩展扩大重构。
